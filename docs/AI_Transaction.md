# MIRAGE 3.0 — Canonical Specification: AI Transaction

> **Status:** Authoritative | **Version:** 3.0.0-draft | **Date:** 2026-10-05
> 
> This document defines the AI Transaction, the fundamental unit of work and traceability in MIRAGE 3.0.
> Terminology is governed by [GLOSSARY.md](GLOSSARY.md) and relates to [MIRAGE_3.0_Specification.md](MIRAGE_3.0_Specification.md).

## 1. Introduction: The AI Transaction Abstraction

In MIRAGE 3.0, every consequential AI interaction is treated as an **AI Transaction**. An AI Transaction is an end-to-end traceable unit of work that encapsulates the entire lifecycle of an AI request, from initial input to final outcome. It is the core abstraction through which MIRAGE enforces control, verification, and governance.

Unlike a simple HTTP request or a single LLM inference call, an AI Transaction models the complex, multi-step, and potentially autonomous behavior of modern AI systems. It accounts for intent classification, risk assessment, context assembly, planning, action execution, outcome verification, and overall assurance scoring.

## 2. The Transaction Record Schema

The Transaction Record is the immutable log of an AI Transaction. It is stored in the Data Plane (MongoDB for flexible trace storage, PostgreSQL for core ledger) and serves as the definitive audit trail.

### Core Identity & Correlation
- `transaction_id`: UUIDv7, primary key for the transaction.
- `tenant_id`: The isolated organizational boundary this transaction belongs to.
- `correlation_id`: Identifier linking this transaction to a broader user session or external request.
- `parent_transaction_id`: If this transaction was spawned by another, its ID (for hierarchical multi-agent scenarios).
- `actor`: Verifiable identity of the initiator (user, agent, system).
- `agent_id`: Identifier of the specific AI agent processing the transaction.
- `session_id`: Identifier grouping multiple transactions in a logical conversation/session.

### Intent & Input
- `intent`: Classified purpose of the request (e.g., "data_extraction", "system_modification").
- `input`: The original user or system request, sanitized by Gate 1 (Input Assurance).
- `input_hash`: Cryptographic hash (SHA-256) of the raw input for non-repudiation.

### Context & Routing
- `context_sources`: List of evidence, memory items, and tool results, each with provenance metadata.
- `taint_flags`: Set of active Information Flow Control taints (`TAINT_UNTRUSTED`, `TAINT_CONFIDENTIAL`).
- `model_id`: The specific model used for core processing.
- `model_version`: Exact version/snapshot of the model.
- `routing_decision`: The rationale for selecting the model (cost, risk, capability).

### Execution & Turn-Loop State
- `turn_count`: Integer counter of executed ReAct cycles (bounded by `max_turns`).
- `turn_records`: Array of individual turn execution traces:
  - `turn_index`: 0-indexed turn number.
  - `reasoning_trace`: Intermediate cognitive generation.
  - `action_contract_id`: Reference to executed action contract.
  - `tool_call`: Parameter payload and execution latency.
  - `outcome`: Verified outcome tuple `(OutcomeStatus, EpistemicConfidence)`.
  - `taint_mutation`: Any new taint introduced by tool output.
- `plan`: The evolving sequence of intended actions generated by the agent.
- `capabilities_used`: The specific capabilities authorized and exercised during this transaction.
- `actions`: Detailed records of state-changing operations, mapping to AI Action Contracts, including preconditions, postconditions, and outcomes.

### Governance & Risk
- `policy_decisions`: Comprehensive list of policies evaluated, inputs to the policies, and deterministic results (Allow/Deny/Transform).
- `approvals`: List of explicit human or policy approvals requested and granted (if risk exceeded autonomy levels).
- `risk_assessment`: Composite risk score, including instantaneous action risk and sliding-window aggregate blast radius consumption.

### Resource Consumption
- `budget`: The allocated limits for this transaction, consumed amounts, and remaining balances per dimension (tokens, time, tool calls, turn count).
- `cost`: Precise attribution of costs: inference cost, tool cost, and total monetary value.
- `latency`: Per-stage latency breakdown (Input, Context Assembly, Execution Turns, Verification, etc.).

### Results & Assurance
- `output`: The final generated response or structured data.
- `output_hash`: Cryptographic hash of the output.
- `outcome`: The composite result of reality verification (Gate 4 / Gate 5).
- `assurance_decisions`: Final verdicts from the Assurance Scorer.
- `gate_results`: Individual decisions, scores, and metadata from Input, Context, Action, Outcome, and Output gates.
- `provenance_chain`: The cryptographically verifiable lineage of how the output was produced.

### Lifecycle Metadata
- `timestamps`: Microsecond-precision timestamps for: `created_at`, `gate_1_complete`, ..., `completed_at`.
- `final_disposition`: The ultimate state of the transaction. Allowed values: `COMPLETED`, `FAILED`, `BLOCKED`, `CANCELLED`, `TIMEOUT`, `PARTIAL`.

## 3. Transaction Lifecycle States and Transitions

An AI Transaction progresses through a governed state machine supporting iterative turn loops:

```
[PENDING]
   │
   ▼ (Gate 1: Input Assurance)
[ANALYZING] ──(Policy Block / Injection)──► [BLOCKED]
   │
   ▼
[ASSEMBLING_CONTEXT] (Gate 2: Context Assurance & Taint Assignment)
   │
   ▼
┌─────────────────── 🔄 THE GOVERNED TURN LOOP ───────────────────┐
│                                                                 │
│  [TURN_REASONING] ──► Agent generates plan turn & tool call     │
│        │                                                        │
│        ▼ (Gate 3: Action Assurance & Aggregate Blast Radius)    │
│  [AUTHORIZING_ACTION] ──(Approval Required)──► [AWAITING_APPROVAL]
│        │                                              │         │
│        ▼ (Authorized)                        (Approved)         │
│  [EXECUTING_TOOL] ──► Tool Proxy invokes MCP / external API     │
│        │                                                        │
│        ▼ (Gate 4: Outcome Assurance & Epistemic Verification)   │
│  [VERIFYING_OUTCOME] ──► Checks postconditions                  │
│        │                                                        │
│        ▼                                                        │
│  [UPDATING_CONTEXT] ──► Updates taint & memory; checks budget   │
│        │                                                        │
│   (More turns needed? turn_count < max_turns)                   │
└────────┬────────────────────────────────────────────────────────┘
         │ (Loop Finished: Agent outputs response, or max turns reached)
         ▼
[VERIFYING_OUTPUT] (Gate 5: Output Assurance — Verification Engine)
         │
         ▼
    [COMPLETED] / [PARTIAL]
```

1. **PENDING**: Transaction initialized, awaiting Gate 1 processing.
2. **ANALYZING**: Intent classification, initial risk assessment, taint seeding, and policy evaluation (Gate 1).
3. **ASSEMBLING_CONTEXT**: Gathering context, evidence, and memory; applying IFC rules (Gate 2).
4. **TURN_REASONING**: Agent generates intermediate plan and proposed action.
5. **AUTHORIZING_ACTION**: Gate 3 validates capabilities, parameter schema, and sliding-window aggregate risk.
6. **AWAITING_APPROVAL**: High-risk action (L4) suspended awaiting human/policy sign-off.
7. **EXECUTING_TOOL**: Tool Proxy executes the external action.
8. **VERIFYING_OUTCOME**: Reality Verifier confirms postconditions according to target epistemic observability class.
9. **UPDATING_CONTEXT**: Tool response sanitized, taint updated, state returned to agent for next turn.
10. **VERIFYING_OUTPUT**: Agent emits final text/payload; Verification Engine evaluates factual consistency.
11. **COMPLETED**: Transaction finished successfully.
12. **FAILED**: Terminal unrecoverable error.
13. **BLOCKED**: Halted by security policy, injection detection, or assurance block.
14. **CANCELLED**: Terminated by caller or timeout.
15. **PARTIAL**: Multi-step transaction where some actions succeeded and others failed.

## 4. Idempotency

MIRAGE 3.0 requires idempotency for safe retries and duplicate request handling.
- Every transaction MUST supply a unique `idempotency_key`.
- The Execution Plane checks the `idempotency_key` against recent transactions for the same `tenant_id`.
- If a match is found and the previous transaction is `COMPLETED`, MIRAGE returns the cached `output` and `outcome` without re-executing actions.
- If a match is found and the previous transaction is in progress, the request blocks and attaches to the existing transaction's result stream.

## 5. Retry Semantics

Not all stages of an AI Transaction are safely retriable.
- **Retriable**: Context assembly, model routing, model inference (if no side-effects), idempotent tool calls (e.g., READ operations).
- **Non-Retriable**: Non-idempotent tool calls (e.g., sending an email, processing a payment) unless a clear failure outcome is verified and the action contract supports safe retry.
- **System Retries vs. Agent Retries**: MIRAGE platform retries happen at the infrastructure layer (e.g., network timeouts). Agent retries happen at the cognitive layer (e.g., the model realizing a tool failed and trying a different approach). Both consume the transaction's `budget`.

## 6. Partial Failure

In multi-step plans, some actions may succeed while others fail.
- A transaction enters the `PARTIAL` state if a non-critical action fails but the agent can still fulfill the core intent, OR if a critical action fails after other state-changing actions have succeeded.
- MIRAGE triggers the **Rollback/Compensation** phase for failed critical paths.
- The `outcome` field must explicitly detail which parts of the plan succeeded and which failed.

## 7. Cancellation

In-progress transactions can be cancelled via API or timeout.
- Cancellation sets a `cancel_requested` flag on the transaction context.
- The Execution Plane checks this flag before every state transition and tool invocation.
- If flagged, the transaction halts, logs the state, attempts compensation for already executed actions (if defined in the Action Contract), and transitions to `CANCELLED`.

## 8. Streaming Behavior

Streaming responses (e.g., Server-Sent Events for LLM generation) interact carefully with the transaction model.
- **Output Assurance (Gate 4)**: Must operate on chunked streams or buffer the stream until semantic boundaries (sentences/paragraphs) are reached to perform verification.
- **Transaction Log**: The transaction record is not finalized until the stream completes. A preliminary record is created, and the final `output_hash` and `assurance_decisions` are appended upon stream closure.

## 9. Asynchronous Behavior

For long-running tasks, MIRAGE supports asynchronous transactions.
- The transaction returns an immediate `ACCEPTED` response with a status endpoint.
- Execution continues in background workers.
- Approvals (Gate 3) pause execution. The transaction sleeps, saving state, until the approval is granted or denied via a webhook/callback.

## 10. Multi-Agent Transactions

When an agent delegates to another agent, MIRAGE tracks this via a Parent/Child hierarchy.
- **Delegation**: The primary agent initiates a new transaction, setting its own `transaction_id` as the child's `parent_transaction_id`.
- **Isolation**: The child transaction has its own budget, risk assessment, and policy evaluation, scoped by the capabilities passed down from the parent.
- **Rollup**: The child's outcome, cost, and assurance score roll up to the parent's `context_sources` and total budget consumption.

## 11. Audit Requirements

The Transaction Record is a foundational compliance artifact.
- **Retention**: Configured per-tenant, but immutable for the duration of the retention period.
- **Completeness**: A transaction record MUST contain enough information to deterministically explain *why* an action was taken, referencing specific policies, context evidence, and risk scores.
- **Tamper-Evidence**: The `provenance_chain` utilizes SHA-256 hashing linking back to the origin, stored in the cryptographically chained Audit Service.

## 12. Transaction Correlation

Related transactions are grouped for analysis and context.
- `session_id` groups transactions in a conversational thread.
- `correlation_id` links MIRAGE transactions to external enterprise systems (e.g., a Jira ticket ID or Datadog trace ID).
- Memory systems use correlation IDs to build associative graphs of user intent over time.

## 13. Concurrency, Parallel Tool Calls, and Escape Prevention

To ensure an agent cannot bypass MIRAGE controls through parallelism or nesting:

### 13.1 Parallel Tool Calls as Atomic Action Batches
When modern models emit multiple tool invocations in a single reasoning turn (e.g., OpenAI parallel function calling `tool_calls: [call_1, call_2, ...]`), Action Assurance treats the set as an **Atomic Action Batch**:
- **Summed Blast Radius:** The cumulative blast radius is evaluated across the aggregate parameters of all proposed calls *before* any tool is dispatched.
- **Race Condition Prevention:** Evaluating parallel calls sequentially in asynchronous threads would permit race conditions against sliding-window budgets. Atomic batch evaluation evaluates the sum against the active quota in a single Redis transaction.
- **Batch Fail-Closed:** If any tool call in the parallel batch is rejected or requires human approval (L4), the entire batch halts.

### 13.2 Sandbox Subprocess and Network Confinement
For agents executing arbitrary code (e.g., Python code interpreters):
- Code executes inside hardened microVMs/sandboxes with zero ambient network access.
- Subprocesses spawned within the sandbox inherit all restrictions; raw network sockets, DNS queries, and outbound connections are blocked at the kernel/container level.
- All external interactions MUST route through the explicit MIRAGE Tool Proxy RPC.

### 13.3 Child Transaction Confinement
An agent cannot escape governance by spinning up sub-agents:
- Child transactions can ONLY be instantiated through the governed `delegate_task` capability.
- Child transactions automatically inherit the parent's taint tags (`TAINT_UNTRUSTED`, `TAINT_CONFIDENTIAL`), policy boundaries, and a sub-allocated slice of the parent's budget.
- A child transaction CANNOT be granted higher autonomy or greater capabilities than its parent.
